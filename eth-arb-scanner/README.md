# Ethereum arbitrage observer

Сканер Ethereum mainnet для Ubuntu. Отслеживает циклы **WETH → токен → WETH** между Uniswap V2, Uniswap V3 (включая разные комиссии) и SushiSwap V2. Ежедневная сводка в Telegram, по умолчанию в **21:00 Europe/Berlin**, с автоматическим переходом на летнее время.

**Режим только наблюдения.** Приватный ключ не нужен. Код не подписывает и не отправляет транзакции, не размещает одобрения токенов в сети. Положительный результат означает успешный `eth_call` на конкретном блоке, а не полученный доход или гарантию будущего исполнения.

## Первый запуск на Ubuntu

Нужны Git, Docker Engine и плагин Docker Compose: [официальная инструкция Docker для Ubuntu](https://docs.docker.com/engine/install/ubuntu/). Команды выполняются пользователем с доступом к Docker. Если репозиторий уже клонирован, используйте существующую копию.

```bash
git clone https://github.com/Vasyl2002/my-project.git
cd my-project/eth-arb-scanner
cp .env.example .env
chmod 600 .env
nano .env
```

Заполните `RPC_HTTP_URL`. Подойдёт личный бесплатный Ethereum mainnet endpoint Alchemy с поддержкой `eth_call` state overrides и адресации блока по хешу (EIP-1898). `RPC_WS_URL` необязателен: без него опрос каждые 30 секунд. Не используйте URL другой сети.

Для Telegram:

1. Создайте бота через **@BotFather** и внесите токен в `TELEGRAM_BOT_TOKEN` в `.env` на сервере.
2. Откройте своего бота и нажмите **Start**.
3. Выполните команду ниже: она выводит только идентификаторы чатов, без токена и текста переписки. Выберите свой `chat_id` и внесите в `TELEGRAM_CHAT_ID`.

```bash
docker compose build
docker compose run --rm scanner node src/telegram-setup.js
```

Проверка и запуск:

```bash
docker compose run --rm scanner node src/check.js
docker compose up -d
docker compose logs --tail=100 -f scanner
```

`check.js` проверяет сеть, state overrides, каноничность адресов пулов и выполняет пробные обменные циклы на текущем блоке. Отрицательный `net` при успешной проверке нормален. Все суммы в JSON выражены в wei WETH; 1 WETH = 10^18 wei.

Проверить сводку локально или отправить тестовую:

```bash
docker compose exec scanner node src/report-cli.js
docker compose exec scanner node src/report-cli.js --send
docker compose ps
```

Тестовая отправка не меняет расписание. Если Telegram не настроен, сканирование работает, а отчёт доступен в консоли. Если бот не доставил сводку, отправщик повторяет попытку; после успешной доставки дату сохраняет в SQLite. При редком сбое сразу после доставки, до записи в БД, возможен дубль (Telegram не предоставляет ключ идемпотентности).

## Обновление

Обновление фактических результатов: все завершённые и подтверждённые текущим блоком симуляции (кандидаты, контроль, повторные проверки) сохраняются в SQLite, включая убыточные и положительные ниже порога. Сводка показывает три разных маршрута с лучшим итогом после газа для каждого: источник проверки, блок, сумма входа/выхода, прибыль до газа, бюджет газа и итог. Суммы выводятся точно в ETH/WETH; это результаты симуляций, не совершённые сделки.

Отдельные категории: итог ≤0; итог >0, но ниже `MIN_NET_PROFIT_ETH`; итог ≥ порога. Порог сохраняется с результатом, поэтому последующее изменение `.env` не переклассифицирует прошлые проверки. Старый счётчик сигналов теперь явно называется «достигли действовавшего порога прибыли». Итоги разных блоков не складываются в доход; одинаковый блок/маршрут/сумма/тип проверки не дублируется. После обнаружения смены хеша накопленные результаты консервативно исключаются из рейтинга. Подробные записи хранятся 30 дней.

Таблица результатов создаётся автоматически при обновлении с сохранением существующей статистики. Полные результаты старых симуляций, для которых были сохранены только счётчики, восстановить нельзя; новый рейтинг начинает заполняться после перезапуска.

Обновление диагностики: новая сводка показывает три ближайших маршрута с ценовым разрывом до/после комиссий и причиной отсеивания, средний/p95/максимальный интервал снимков и успешность чтений каждого пула. Это оценки цен, а не исполнимая прибыль; в Telegram выводятся общая доступность и до трёх адресов с наибольшей долей ошибок.

Раз в **6 часов**, начиная с первого подходящего снимка после обновления, выполняется один контрольный полный обмен независимо от ценового фильтра. Используется минимальная сумма из `TRADE_SIZES_ETH`; маршруты чередуются среди трёх ближайших на текущем снимке. Контроль входит в `MAX_SIMULATIONS_PER_BLOCK` и общий лимит RPC. Интервал можно менять через необязательный `CONTROL_INTERVAL_HOURS` (1–168); существующий `.env` получает значение 6 автоматически. Время последней попытки сохраняется между перезапусками, в том числе при ошибке, чтобы не расходовать квоту повторными попытками. Если нет двух читаемых сопоставимых пулов или исчерпан RPC-бюджет, контроль откладывается.

Контрольные результаты показаны отдельно от симуляций кандидатов: вход, выход, бюджет газа и итог, включая отрицательные значения. Неподтверждённый блок не даёт успешного контрольного результата. Новые метрики начинают собираться после обновления; прежние данные SQLite сохраняются. Пропуски блоков теперь учитываются только после успешного снимка, без повторного начисления при ошибках. Счётчик смен хеша не утверждает, что причиной была именно реорганизация сети; отсутствие блока в ответе RPC отмечается как ошибка чтения.

Длинные сводки автоматически делятся на сообщения до 3500 символов. При сбое отправка продолжается с первой недоставленной части; подтверждённые части не отправляются повторно. Редкий сбой процесса между доставкой части и записью подтверждения в SQLite всё ещё может дать дубль.

Из папки `my-project/eth-arb-scanner`:

```bash
git pull --ff-only
docker compose up -d --build
docker compose logs --tail=50 scanner
```

`.env` не хранится в Git. Статистика находится в именованном Docker volume `scanner-data` и сохраняется при пересборке. **Не выполняйте `docker compose down -v`, если нужна статистика.** Для остановки используйте `docker compose stop`. Процесс запускается автоматически после перезагрузки Docker. Порты наружу не открываются.

## Почему выбраны эти пулы

Начальный список адресов токенов: LINK, UNI, AAVE, LDO, CRV, COMP, SUSHI, WBTC, wstETH и rETH. Это ограниченный список для проверки рыночной гипотезы, не рекомендация покупать токены. Подбор выполняется заново каждый день; токен включается только при наличии минимум двух подходящих WETH-пулов.

Алгоритм:

- Отбирает пулы из DEX Screener с ликвидностью от $20 000 и суточным объёмом от $500. Эти долларовые данные нужны только для предварительного отбора, в расчёт прибыли не входят.
- Для каждого токена берёт наиболее глубокий опорный пул и активный альтернативный пул, ранжируя альтернативы по отношению объёма к ликвидности. При свободном лимите добавляет третью площадку/комиссию.
- Ограничивает выборку 24 пулами, чтобы сохранить разнообразие токенов и небольшую нагрузку на бесплатный RPC.
- Читает `token0`, `token1`, `factory`, `fee` непосредственно из контрактов и проверяет адрес через `getPair`/`getPool` известной фабрики. Случайный контракт с названием WETH или копия интерфейса не проходит такую проверку.

Сочетание глубокого и меньшего активного пула может давать расхождения после сделок. Это проверяемая гипотеза: здесь конкурируют другие боты, и прибыльных результатов может не быть. Маленькие новые токены, новые фабрики, V4, Curve, Balancer, мосты и маршруты из трёх и более обменов в эту версию не включены. Сканер не предназначен для эксплуатации ошибок протоколов.

Снимок первоначального отбора и причины: [POOL_SELECTION.md](POOL_SELECTION.md). Текущий фактический список хранится в SQLite; доступен командой `node src/status.js` внутри контейнера. Сбой обновления списка сохраняет прежнюю выборку и отмечается в статистике.

## Как проверяется сигнал

1. WS сообщает об изменении выбранных пулов; HTTP-опрос остаётся резервным. Не чаще раза в 12 секунд выполняется согласованный снимок пулов через Multicall3, привязанный к хешу блока.
2. Цена из резервов V2 или `sqrtPriceX96` V3 используется только как предварительный фильтр. Из неё вычитаются комиссии обоих пулов. Эта цена не считается исполнимой котировкой.
3. Для кандидатов проверяются суммы `TRADE_SIZES_ETH`. Лимит по умолчанию — четыре симуляции за проход, включая повторные проверки; остальные кандидаты могут быть пропущены. Суммы перебираются с ротацией.
4. В **одном `eth_call`** код `Probe.sol` виртуально помещается на пустой адрес через state overrides. Виртуальный ETH превращается в WETH, происходит покупка через реальный роутер, затем продажа фактически полученного токена через второй роутер. Изменения первой сделки видны второй. Ничего не записывается в Ethereum.
5. Из изменения WETH-баланса вычитается консервативный бюджет газа: `(измеренный газ + 50 000) × 1.25 × (2 × baseFee + priorityFee)`. Надбавки настраиваются. Это бюджет, а не точная стоимость будущей транзакции; платежи билдерам/MEV сюда не входят.
6. Положительный результат сохраняется, только если блок остался каноническим. Маршрут повторно проверяется на следующем доступном снимке (не обязательно следующем блоке), максимум через пять блоков. Пропущенная проверка не считается успехом.

При расхождении хеша сканер проверяет сохранённую историю до общего канонического предка. Ожидающие проверки записи временно исключаются из итогов; подтверждённые сохраняются, а сигналы расходящихся блоков не перепроверяются. Подробности — в разделе о точечной проверке истории ниже.

`Probe.sol` — **только для симуляций**. Не разворачивайте и не переводите на него средства: в нём нет защиты торгового контракта, минимального выхода и вывода средств. Приложение использует только runtime-bytecode в `eth_call`.

## Бесплатные квоты и устойчивость

Настройки по умолчанию ограничивают HTTP RPC 15 000 попытками в сутки UTC; счётчик переживает перезапуск. Сканер автоматически увеличивает интервал по оставшемуся лимиту и времени до полуночи UTC: при стандартных настройках в начале суток это примерно 48 секунд, затем интервал пересчитывается. Это сознательный компромисс между охватом и бесплатной квотой. Это не CU и не реальная квота провайдера. Стоимость Multicall/симуляций и WS-трафика зависит от провайдера. Контролируйте фактический расход в его кабинете. При достижении локального лимита сканирование приостанавливается до следующего дня, сводки продолжают работать.

После обрыва WS сканер переподключается; HTTP остаётся рабочим. Пропущенные блоки фиксируются как пробел наблюдений: исторические возможности не восстанавливаются и не выдаются за проверенные. При перезапуске повторно проверяются незавершённые сигналы, если они ещё достаточно свежие. Healthcheck становится нездоровым после пяти минут без успешного снимка. Docker сам по себе не перезапускает контейнер только из-за unhealthy; при падении процесса работает `restart: unless-stopped`.

Сводка отражает интервал от предыдущей успешной сводки; при первом запуске — последние 24 часа, фактически доступные в БД. Хранение подробных событий — 30 дней. Показаны уникальные маршруты и лучшие отдельные результаты, **не сумма «заработка»**. Отчёт также показывает ошибки, пропуски наблюдений, возраст последнего блока и счётчик RPC.

## Детали газа и уточнение суммы

Новые симуляции сохраняют измеренный внутри Probe расход газа, base fee блока, настроенный tip и запас. Оценка комиссии блока: `(gasUsed + 50000) * (baseFee + tip)`. Консервативный бюджет остаётся прежним: `floor((gasUsed + 50000) * (10000 + GAS_MARGIN_BPS) / 10000) * (2 * baseFee + tip)`. Накладные 50 000 единиц — допущение, а внутренний gasleft не является квитанцией транзакции и не учитывает итоговые возвраты газа. Ни одна оценка не гарантирует включение сделки или фактическую стоимость исполнения.

Сводка показывает обе оценки, число положительных результатов по комиссии блока и цену безубыточности `floor(gross / (gasUsed + 50000))` в wei/gas, представленную в gwei. Это суммарная цена base fee + tip для нулевого итога, без порога прибыли. При неположительной прибыли обменов цена не выводится. Сигналы и повторные проверки по-прежнему используют консервативный бюджет и MIN_NET_PROFIT_ETH. Для записей до обновления детали не восстанавливаются задним числом.

В последнем доступном слоте симуляций (если свободных слотов было хотя бы два) проверяется промежуточная сумма около лучшего результата текущего блока с положительной прибылью до газа. Берётся середина между этой суммой и соседней большей точкой сетки; у верхней границы — меньшей. Все суммы ограничены минимумом и максимумом TRADE_SIZES_ETH. При отсутствии подходящего результата используется обычная сетка. Это одно локальное уточнение, а не гарантия нахождения оптимума. Ротация обычных размеров продолжается; общий лимит симуляций и суточный лимит RPC не увеличены. Новые переменные .env не требуются.

## Связь сигнала с повторной проверкой

Повтор сохраняет исходные hash блока, номер блока, маршрут, сумму, расчётный итог и известный порог. Сводка показывает номер блока повтора, расстояние в блоках, выход, бюджет газа, итог и его изменение. Положительный итог ниже порога явно отделяется от неположительного. Ошибка симуляции и истечение срока не считаются убытком.

Отдельный раздел включает последние 10 повторов, выполненных за отчётный период, даже если исходный сигнал попал в предыдущую сводку. Возле лучших сигналов также показан статус повтора. Для старых записей без точной связи выводится, что связь неизвестна; данные не сопоставляются по одному названию токена. Инвалидированные симуляции исключаются. Из двух снимков нельзя установить точный момент исчезновения возможности между блоками.

Обновление не требует новых настроек, миграции базы или дополнительных RPC-запросов.

## Точечная проверка истории и быстрый повтор

При несовпадении хеша сканер помечает историю как ожидающую проверки (`valid=-1`), а подтверждённо расходящийся блок и повторы его сигналов — недействительными (`valid=0`). Проверка идёт назад по сохранённым блокам до общего канонического предка; более ранняя история возвращается в отчёт. За проход проверяются максимум 8 хешей. Отсутствующий ответ RPC оставляет записи ожидающими проверки, а не превращает их в недействительные. Состояние переживает перезапуск. Старые записи, исключённые прежней версией, автоматически не восстанавливаются. Метод предполагает согласованные ответы RPC о канонической цепочке.

При наличии сигнала новый блок проверяется примерно каждые 3 секунды отдельным проходом без чтения всех пулов и поиска новых маршрутов. Этот проход не считается полным снимком рынка. Повторы получают приоритет над контрольными симуляциями и обновлением списка пулов. Для ускорения резервируется минимум из 300 HTTP-попыток и 10% суточного лимита; обычный поиск учитывает резерв. Перед быстрым проходом проверяется запас на худший случай, включая повторы RPC и проверку истории. При недостатке резерва очередь обрабатывается обычным сканированием. Общий суточный лимит не повышается. Попадание ровно в следующий блок зависит от задержек RPC и длительности обработки и не гарантируется.

Сводка отдельно показывает ожидающую проверки историю и быстрые проходы; успешные повторы считаются только по действительным сохранённым результатам. Схема SQLite обновляется автоматически, `.env` менять не нужно.
